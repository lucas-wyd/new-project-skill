# Domain language

Use when ambiguous or specialized domain terms materially affect product, design, or implementation decisions. A domain glossary is maintained project vocabulary, not a general project summary.

When a relevant `CONTEXT.md` exists, treat it as the domain glossary unless the repository establishes another meaning. If a `CONTEXT-MAP.md` maps several domains, follow it to the glossary for the affected area.

Create a glossary only after useful terms or relationships are established. Keep it limited to stable terms, meanings, relationships, and resolved ambiguities. Keep implementation decisions, plans, approvals, current status, and private planning details in their authoritative documents.

Prefer a tracked project document so its vocabulary travels with the code. Add a concise pointer from the active instruction file stating which work requires the glossary, such as naming domain concepts or changing domain behavior. Build the glossary from established domain terms and relationships; keep `AGENTS.md` focused on project instructions.
